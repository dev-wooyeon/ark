## 주문이 어디서 멈췄는지 한곳에서 볼 수 있을까요?

Temporal 전환기의 출발점은 운영팀의 질문이었어요. 주문이 어디서 멈췄는지 답하려면 주문팀, 중개시스템팀, 접수채널팀의 로그를 추적하고 대조해야 했어요. 각 시스템이 이벤트를 받아 자기 일을 처리하더라도, 주문 하나의 전체 진행 상황을 바로 설명하기는 어려웠어요.

실패한 이벤트를 다시 발행하는 일도 단순하지 않았어요. 소비처가 여러 곳이면 이미 처리한 곳에 어떤 영향을 줄지 함께 고려해야 해요. 실패를 발견하는 것과 안전하게 복구하는 것은 별개의 문제였어요.

발표에서는 주문의 진행과 이력을 중앙에서 관리하기 위해 Temporal을 도입한 과정을 설명했어요. 직접 오케스트레이터를 만들면 워커 장애, 재시도, 취소, 보상, 동시성 제어를 모두 다뤄야 해요. 직접 만들었다면 이런 동작도 하나씩 구현해야 했겠죠.

도입 뒤에도 운영에 맞춘 설계는 필요했어요. DB I/O를 관측하고 클러스터별로 DB를 구성하는 문제도 있었지만, 특히 눈에 들어온 건 실패한 작업을 다시 처리하는 방법이었어요. 실패 원인이 사라졌다고 해서 주문 전체를 처음부터 실행할 수는 없잖아요. 발표팀은 실패했던 단계를 골라 다시 시도할 수 있는 복구 방식을 만들었어요.

흐름을 코드에 드러내는 작업도 필요했어요. 외부에서 들어오는 신호인 Signal은 상태 머신의 검증을 거쳐 상태를 바꾸고, 실제 진행 순서는 Workflow 본문에서 다루도록 정리한 거예요.

저도 워크플로우의 흐름을 설계하고 있어서, 각 스텝을 독립적으로 실행하는 방식이 특히 기억에 남았어요. 전체를 한 트랜잭션으로 묶어 모두 성공하거나 모두 실패하게 만드는 방식과는 다른 고민이었거든요. 각 단계가 어디까지 끝났는지 남기고, 실패한 단계는 다시 처리할 수 있도록 구분하는 거죠.

특히 실패한 스텝을 다시 처리할 수 있는 상태로 두고, 필요하면 수동으로 실행할 수 있다는 점이 기억에 남았어요. 어디까지 자동으로 재시도하고 언제 사람이 개입할지, 이미 끝난 작업과의 관계는 어떻게 다룰지 같은 정책도 많이 고민했을 것 같아요. 워크플로우를 설계할 때 정상적인 실행 순서만큼 실패 이후의 흐름도 구체적으로 그려봐야겠다는 생각이 들었어요.

## 대화로 쿠폰을 만들어도 검증은 필요해요

쿠폰 하나를 만들 때도 할인 유형, 적용 범위, 사용 조건처럼 정할 것이 많아요. 조건끼리 영향을 주기 시작하면 화면을 자주 쓰는 사람도 신경 쓸 일이 늘어나죠. 헤드리스 어드민 세션은 이렇게 복잡해진 쿠폰 관리 화면을 다뤘어요.

헤드리스 어드민은 화면을 조작하는 대신 AI와 대화하면서 관리 작업을 수행하는 방식이에요. 이 사례에서는 웹 어드민이 쓰던 규칙과 서버 API를 그대로 활용했어요. 사용자는 대화로 요청하고, 기존 로직이 그 요청을 검증하고 처리하는 거예요.

쿠폰 이름에는 15% 할인이라고 써놓고, 실제 할인율은 10%로 설정한 사례도 있었어요. 이름과 할인율이 각각의 입력 조건을 만족하면 검증을 통과할 수 있지만, 고객에게 보여주는 내용과 실제 혜택은 달라져요. AI는 두 값을 함께 읽고 이 어긋남을 짚어줬어요. 각 입력값만 따로 검사해서는 놓칠 수 있는 문제였어요.

그렇다고 웹 어드민을 없애지는 않았어요. 간단한 작업은 화면에서 바로 끝내는 편이 빠르고, 여러 쿠폰을 나란히 비교하는 일도 UI가 편했어요. 실수하면 안 되는 작업도 오랫동안 사용해 온 웹 UI에 남겨뒀다고 해요.

우리 시스템에도 레거시 어드민이 있어서 더 관심이 갔어요. 저는 코드 에이전트 CLI를 코드를 작성하는 도구로만 봐왔는데, 시연에서는 그 도구로 기존 어드민 API를 호출해 쿠폰을 만들었어요. 같은 기능을 두고도 도구의 쓰임을 다르게 보니, 화면에서 하던 일을 터미널에서 대화로 처리할 수 있다는 점이 인상적이었어요.

## 상품은 합쳤지만 재고 원장은 남겨뒀어요

마지막 세션에서는 B마트와 배민스토어의 상품·재고 시스템을 다뤘어요. 직매입과 외부 셀러 입점이라는 차이가 있지만, 상품은 하나의 도메인 모델로 통합했어요. 반면 재고는 원천을 그대로 두고 조회를 통합하는 전시 재고 시스템을 선택했어요.

상품에서는 공통 기준을 만드는 일이 중요했어요. 우유의 용량이 한쪽에는 1000ml, 다른 쪽에는 1L로 기록돼 있다면 문자열만으로 같은 조건을 검색하기 어려워요. 판매처에 관계없이 유지되는 상품 속성을 카탈로그로 관리해야 함께 찾고 비교할 수 있어요.

지점별 가격을 관리하는 예시도 이해하기 쉬웠어요. 본사 상품 100개의 가격을 바꿀 때 지점이 1만 개라면, 모든 지점이 값을 복제해서 가진 구조에서는 최대 100만 건을 바꿔야 해요. 대부분 본사 가격을 따르는데도요.

그래서 공통값은 본사에 두고 지점에서 달라지는 값만 따로 관리해요. 지점 가격이 있으면 그 값을 쓰고, 없으면 본사 가격을 따르는 방식이죠. 저장할 데이터가 줄어드는 대신, 읽을 때 어느 값을 적용할지 판단해야 해요.

재고는 소유권이 달랐어요. 외부 셀러의 재고 원장을 플랫폼이 모두 소유할 수 없으니 상품과 같은 방식으로 합치기 어려웠어요. 발표에서는 원천별 차이를 연결하면서 조회에 필요한 재고 정보를 제공하는 구조를 설명했어요.
